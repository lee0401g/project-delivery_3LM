# 補充教材：模型選擇與比較

## 選擇原則

**較大的模型通常具有較好的理解與整理能力，但會占用更多記憶體並降低回答速度**；
**較小的模型下載較快且容易執行，但面對複雜問題、長文件或跨文件整理時可能較不穩定**

## 參數量與模型檔案

- `2B`、`3B`、`3.8B`、`4B` 與 `8B` **表示模型約有多少十億個參數**
- 模型檔案容量是下載後占用的磁碟空間，**不等於執行時實際使用的 RAM 或 GPU 顯示記憶體**
- 執行時還需要額外空間儲存對話內容、上下文與其他推理資料，因此**不能只用模型檔案容量判斷電腦是否足夠**
- 相同規模的模型也可能因量化方式不同而有不同的檔案大小與硬體需求

## 模型標籤

模型標籤用來指定模型系列與規模
```text
gemma3:4b
```

其中 `gemma3` 是模型系列，`4b` 是模型規模；使用完整標籤可避免 `latest` 未來指向不同模型規模

## 什麼是量化

同一個模型可能提供不同的量化版本，例如

```text
granite4.2:3b-q4_K_M
granite4.2:3b-q6_K
granite4.2:3b-q8_0
granite4.2:3b-bf16
```

其中 `granite4.2` 是模型系列，`3b` 是模型規模，最後的 `q4_K_M`、`q6_K`、`q8_0` 或 `bf16` 表示模型權重使用的儲存精度

量化的主要目的，是在模型品質、檔案大小與硬體需求之間取得平衡

| 類型 | 大致特性 |
| --- | --- |
| Q2、Q3 | 檔案較小、硬體負擔較低，但品質可能有較明顯損失 |
| Q4 | 常見的平衡選擇，適合先測試一般本機環境 |
| Q5、Q6 | 使用更多空間，通常可保留較多模型資訊 |
| Q8 | 更接近高精度版本，但需要較多記憶體 |
| BF16 | 高精度版本，檔案與硬體需求通常最高 |

不需要把每一種量化格式都視為不同模型，它們通常是同一模型的不同儲存方式

量化名稱不能直接保證回答品質，實際結果仍會受到模型、問題、提示詞、上下文與硬體影響

對一般本機使用而言，不需要一開始就選擇最高精度版本，可先從 Q4 左右的版本測試，再依速度、記憶體用量與回答品質調整

## 模型比較

| 定位 | Ollama 模型標籤 | 開發者 | 模型檔案約 | 授權 | 適用情況 |
| --- | --- | --- | ---: | --- | --- |
| 主要方案 | `gemma3:4b` | Google | 3.3 GB | Gemma Terms | 中文問答、摘要、圖片與 RAG |
| 最低負擔 | `granite3.3:2b` | IBM | 1.5 GB | Apache 2.0 | 優先確保速度與可執行性 |
| 平衡方案 | `phi4-mini:3.8b` | Microsoft | 2.5 GB | MIT | 一般問答、推理與數學 |
| 品質優先 | `granite3.3:8b` | IBM | 4.9 GB | Apache 2.0 | 摘要、RAG 與較複雜的整理 |
- Google Gemma 3 官方資料列出超過 140 種語言、問答、摘要、推理與圖片理解等能力
- IBM Granite 3.3 官方資料列出中文、多語對話、摘要、問答與 RAG 等支援能力
- Microsoft Phi-4 Mini 官方資料列出中文與多語支援，並著重推理及數學能力

表中的定位僅供比較，不代表不同模型在所有問題上都會得到相同排名

## 硬體選擇參考

以下選擇參考以 16 GB RAM 與至少 50 GB 可用 SSD 空間為基準

| 使用情況 | 優先候選 | 說明 |
| --- | --- | --- |
| 一般本機使用 | `gemma3:4b` | 兼顧中文能力、模型容量與後續 RAG |
| 希望下載快且回答快 | `granite3.3:2b` | 適合先確認整套環境可以運作 |
| 需要一般問答與推理 | `phi4-mini:3.8b` | 模型容量與能力較平衡 |
| 重視摘要與 RAG 品質 | `granite3.3:8b` | 對硬體與等待時間的要求較高 |
| 電腦執行速度不確定 | `granite3.3:2b` | 先使用最低負擔方案，後續再更換 |

> 沒有 NVIDIA GPU 仍可使用 CPU 執行，但回答速度通常較慢；模型可隨時更換，不需要重新安裝 Ollama 或 Open WebUI

## 上下文設定參考

**上下文是模型在一次回答中可以參考的系統提示、對話歷史、RAG 檢索內容與目前問題**，不是知識庫的總容量；**數值越大會使用越多 RAM 或 GPU 顯示記憶體**

| 上下文 | 適合用途 | 建議 |
| ---: | --- | --- |
| 4K（4096） | 環境測試與簡短單輪問答 | 低硬體備案 |
| 8K（8192） | 一般對話、多輪問答與短文件 RAG | 建議預設 |
| 16K（16384） | 較長文件摘要與較多檢索片段 | 確認硬體充足後使用 |
| 32K（32768） | 多文件比較與較長資料整理 | 不建議作為一般筆電預設 |
| 64K（65536） | 大型文件與複雜工具工作流 | 需要高階硬體 |
| 128K（131072） | Gemma 3 4B 支援上限 | 不建議一般筆電使用 |

建議先使用 8K（8192），若執行太慢或記憶體不足則降為 4K（4096）；進行多文件 RAG 且硬體仍有餘裕時，可測試 16K（16384）

## 模型、量化與上下文的關係

選擇本機模型時，可以把三個概念分開

```text
模型規模
  決定模型容量與能力傾向

量化
  影響模型檔案大小、記憶體需求與精度

上下文
  影響一次可以處理多少對話與文件內容
```

`3B` 描述模型規模，`Q4_K_M` 描述量化方式，`128K` 描述模型支援的上下文長度上限，三者代表不同資訊

模型標示支援 128K，不代表一般電腦應直接設定為 128K；實際設定仍要配合 RAM、GPU 顯示記憶體與使用情境

## 實際選擇流程

一般 16 GB RAM、沒有獨立 GPU 的電腦，可先依下列順序測試

1. 選擇 2B～4B 的模型
2. 優先使用 Q4 左右的量化版本
3. 將上下文先設為 8K（8192）
4. 確認 Ollama 與 Open WebUI 可以正常使用
5. 觀察回答速度與 RAM 使用情形
6. 測試繁體中文問答及課程需要的功能
7. 再進行文件問答與 RAG 測試

若執行速度太慢或記憶體不足：

- 降低模型規模
- 降低量化精度
- 降低上下文

若速度可以接受但回答品質不足：

- 測試較高精度的量化版本
- 改用較大的模型
- 比較不同模型在相同問題上的結果

若只有長對話或文件內容被截斷，再考慮提高上下文，調整前先確認硬體仍有足夠資源

模型選擇不只取決於模型本身，RAG 效果也會受到文件內容、文件切分、索引模型、檢索方式、上下文與提示詞影響

## 常見調整情境

| 情境 | 調整方式 |
| --- | --- |
| `gemma3:4b` 執行太慢 | 改用 `granite3.3:2b` |
| 必須採用 MIT 授權 | 改用 `phi4-mini:3.8b` |
| 願意提高硬體負擔以測試整理品質 | 測試 `granite3.3:8b` |
| 對話或 RAG 內容被截斷 | 在硬體允許時提高上下文 |
| 提高上下文後記憶體不足 | 降低上下文或改用較小模型 |

> 模型由 Ollama 管理，不需要把特定模型寫入 `03_compose.yaml`
